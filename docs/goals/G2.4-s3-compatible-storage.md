# G2.4 — S3-compatible storage

Status: Implementation complete — verification and merge in progress
Issue: [#24](https://github.com/cosZone/koharu-suite/issues/24)  
Parent roadmap: [#1](https://github.com/cosZone/koharu-suite/issues/1)  
Blocked by: G2.3, completed in [#22](https://github.com/cosZone/koharu-suite/issues/22)

## 1. Outcome

G2.4 adds an optional S3-compatible media backend without regressing the G2.3 local-only deployment. An
operator can copy verified content-addressed blobs between local and S3-compatible storage, recover interrupted
operations, protect selected content from policy eviction, preview prune decisions, and apply those decisions
with an auditable reason.

This Goal is complete when a fresh local-only deployment behaves exactly as before and an S3-enabled deployment
can demonstrate:

1. upload or copy a verified blob;
2. serve it through the existing opaque public media URL and authorization gate;
3. resume an interrupted migration;
4. restore a missing location from another healthy location;
5. protect a blob, preview prune, then apply a valid unprotected eviction;
6. fall back to the original Telegram message when no healthy cached location exists.

## 2. Inherited contracts

These are not reopened by G2.4:

- koharu-suite and every media backend remain optional to astro-koharu.
- Canonical messages, revisions, raw source evidence, media metadata, and provenance live in PostgreSQL and do
  not depend on cached bytes.
- Local-only is the default. With no S3 configuration, the process does not construct an S3 client or read S3
  credentials.
- `sha256 + byteLength + detectedMime` is the verified blob identity. An S3 ETag is transport metadata, never
  a content hash.
- Object keys are derived from the canonical SHA-256 namespace. Public APIs expose only suite-owned opaque IDs.
- Existing image, animation/video, per-post, thumbnail, current-revision, tombstone, range, and source fallback
  contracts remain unchanged.
- One physical copy per SHA-256 per backend may serve many objects, messages, and channels.
- No migration or eviction may delete the last healthy copy before its policy allows that outcome and the
  destination or fallback state has been committed.
- Mutations are owner/local-operator only, require an explicit reason, use bounded token-fenced leases, and emit
  redacted audit records.

## 3. Existing seams and required correction

G2.3 deliberately preserved a narrow storage seam but kept local filesystem types in several interfaces.

| Existing area | Keep | Change for G2.4 |
| --- | --- | --- |
| `blob-store.ts` | identity, lease, staging ownership, SHA key, integrity errors | Separate local staging/recovery from persistent backend operations |
| `worker.ts` | `MediaCacheWorkerBlobStore`, settlement protocol | Replace `FileHandle` reads with bounded/cancellable byte streams or ranges |
| `eviction-repository.ts` | claim → physical delete → token-fenced finalize | Target one storage location rather than the global blob identity |
| `public-reader.ts` | opaque ID, current/tombstone gate, opaque ETag, access coalescing | Select a DB-confirmed healthy location through a backend-neutral reader |
| `maintenance-service.ts` | bounded reconcile and audit | Keep local temp-orphan cleanup local; add backend-neutral location verification |
| `runtime.ts` / `config.ts` | read-only server and write-capable worker split | Construct an explicit backend registry; do not load disabled providers |
| PostgreSQL ledger | blobs as immutable content identity | Move physical readiness, budget, LRU, leases, and backend metadata to locations |

The persistent backend contract must express capabilities rather than filesystem primitives:

```ts
interface MediaBlobBackend {
  readonly id: string;
  delete(identity: MediaBlobIdentity, options: MutationOptions): Promise<DeleteResult>;
  head(identity: MediaBlobIdentity, options?: ReadOptions): Promise<HeadResult>;
  open(identity: MediaBlobIdentity, options?: RangeReadOptions): Promise<ReadableStream<Uint8Array>>;
  put(input: VerifiedBlobInput, options: MutationOptions): Promise<PutResult>;
}
```

The final names and exact return types may change during implementation. The important boundary is that S3 is
not forced to emulate hard links, directory fsync, or Node `FileHandle`, while local staging keeps its
crash-safety guarantees.

## 4. Implemented additive data model

The first migration is additive and preserves the G2.3 tables until the local adapter has passed through the new
path.

### `media_storage_backends`

- stable backend ID and kind (`local | s3`);
- operator label and enabled/readable/writable status;
- deterministic read priority;
- physical byte budget and current ready-byte ledger;
- non-secret configuration fingerprint and timestamps.

Secrets, raw credentials, signed URLs, and provider-specific client objects never enter PostgreSQL.

### `media_blob_locations`

- `(backend_id, blob_sha256)` identity;
- canonical derived storage key;
- `copying | ready | deleting | evicted | missing | corrupt` state;
- verified byte length and content hash evidence;
- bounded provider metadata needed for conditional operations, never used as the content identity;
- last access time and token-fenced mutation lease;
- created/verified/updated timestamps.

`media_cache_blobs` continues to represent immutable content identity. A blob's logical references do not change
when one physical location is copied, evicted, missing, or restored.

### Operation and policy records

The existing durable command/audit pattern is extended rather than bypassed. Migration, restore, protection,
policy, and prune carry:

- bounded batch and continuation state;
- source and destination backend IDs;
- dry-run versus apply;
- initiator and reason;
- per-item sanitized result/error;
- lease owner, token, expiry, attempt, and completion timestamps.

The exact protected-mark scope and `evicted_policy` enum remain design-gate decisions below.

## 5. Migration sequence

Implementation must remain deployable after every phase:

1. Add backend/location schema and backfill each ready G2.3 blob as a ready local location. Keep old reads and
   accounting authoritative during this phase.
2. Route the existing local implementation through the backend-neutral read/write/delete contract. Prove
   local-only behavior before enabling S3.
3. Add the S3-compatible adapter, configuration redaction, and a MinIO CI fixture.
4. Add bounded copy planning and apply: claim → stream → verify → publish destination → finalize ready. A
   destination failure leaves the source healthy and the operation resumable.
5. Switch public location selection to the new ledger. Reads must re-check the existing message visibility gate
   and use only DB-confirmed ready locations.
6. Add restore/reconcile, then protection and policy-aware LRU/prune. No policy deletion is enabled before copy
   and read fallback have proven stable.
7. Remove or narrow legacy physical-state columns only in a later generated migration after upgrade and rollback
   tests prove the new ledger. G2.4 need not perform a destructive cleanup migration.

## 6. Crash and concurrency contract

- A database location is never `ready` before the backend has published and verified the complete object.
- Copy/upload is idempotent for the canonical key. A conflicting size or checksum is `corrupt` or an integrity
  conflict, not a successful deduplication.
- Destination verification completes before an operation can make its source eligible for policy deletion.
- Delete is claim → backend delete → token-fenced finalize. Timeout or ambiguous provider results remain
  reconcilable; accounting is not decremented early.
- Migration, restore, public read, access coalescing, LRU, explicit eviction, and protection changes re-check
  current state under the existing media-cache advisory-lock discipline.
- A shared blob is protected according to the accepted aggregation rule, not according to whichever object was
  encountered first.
- All list/reconcile/prune work is page-bounded. A single stale population cannot monopolize the worker.
- Streams, requests, retries, multipart uploads, and cleanup have explicit byte, time, attempt, and concurrency
  limits.

## 7. Public serving

The inherited public URL remains `/api/v1/media/:opaqueId`. Storage backend IDs, keys, buckets, endpoints, signed
URLs, and content hashes remain private.

The implemented delivery mechanism is server proxying:

- it preserves the immediate current-revision/tombstone authorization check;
- it keeps one HEAD/range/ETag/error contract across local and S3-compatible backends;
- it avoids exposing short-lived provider URLs or introducing a second public cache invalidation model.

Direct or presigned delivery remains out of scope because it would require a separate revocation and cache
design.

## 8. Accepted design gate

Accepted on 2026-07-24 as `1A–6A`:

1. S3 is the durable cached tier and local storage is the optional hot tier.
2. Public delivery remains behind the suite server proxy.
3. The first version supports local ↔ S3 migration only.
4. Protection is object-level, aggregates to shared blobs, and blocks policy and explicit eviction until removed.
5. `recache_on_access` is the default; `stay_evicted` is the explicit alternative.
6. MinIO is the CI compatibility baseline and `@aws-sdk/client-s3` is the implementation SDK.

The gate is closed. Schema and mutating implementation must preserve these choices.

### D1. Storage roles and supported modes

- **A — durable S3 tier + optional local hot tier (accepted):** local-only remains supported; in tiered mode,
  S3 is the durable cached copy and local is an evictable hot copy. Public reads prefer local, then proxy S3.
- **B — peer backends:** local and S3 are equal operator-selected targets. This is more flexible but makes
  authority, restore, deletion, and policy harder to explain.
- **C — S3 mirror only:** public reads never use S3 directly. This is simpler but does not deliver a complete
  second serving adapter.

### D2. Public delivery

- **A — server proxy (accepted):** one authorization, range, ETag, and fallback contract.
- **B — presigned redirect:** lower server bandwidth, but needs explicit revocation, expiry, cache, and provider
  compatibility rules.

### D3. Migration directions in v1

- **A — local ↔ S3 only (accepted):** enough for migrate and restore without S3-to-S3 orchestration.
- **B — arbitrary configured backend pairs:** more general, substantially larger operation and credential scope.

### D4. Protected mark

Accepted: owner-created object-level marks with reason and optional expiry. Protection
aggregates upward: if any current object referencing a blob is protected, policy prune cannot remove that blob's
last durable cached location. Explicit owner eviction also fails closed unless protection is removed first.

Alternatives are blob-level only, channel policy, or per-location protection. Those are less legible in the
current Owner Desk or do not safely aggregate shared references.

### D5. `evicted_policy`

Accepted object-level enum:

- `recache_on_access` — public miss keeps the source fallback and queues bounded recache;
- `stay_evicted` — only an explicit owner restore/retry may cache the object again.

Default: `recache_on_access` for ordinary objects; protected objects are not policy-evicted.
No synchronous public request waits for recache.

### D6. S3 compatibility baseline

The implemented baseline covers:

- endpoint, region, bucket, namespace prefix, and path-style toggle;
- explicit environment credentials with all four core settings required together;
- conditional put/head/get-range/delete behavior;
- checksum verification and multipart threshold;
- request timeout, retry, concurrency, and abort cleanup;
- server-side encryption requirements, if any.

The implementation claims compatibility only with the selected CI fixture and explicitly smoke-tested
providers, not every product carrying an S3 label.

#### Accepted SDK baseline

Use [`@aws-sdk/client-s3`](https://github.com/aws/aws-sdk-js-v3) rather than the MinIO JavaScript client:

- command-level abort signals, Smithy connect/request/socket timeouts, standard conditional fields, and explicit
  endpoint/path-style configuration fit the bounded worker contract;
- Cloudflare R2 and Backblaze B2 both document the S3-compatible endpoint/SDK path, while the MinIO client does
  not provide an equally direct `AbortSignal` or create-only conditional-write contract;
- the existing 10 MiB image and 20 MiB animation/video hard limits mean every G2.4 object has a known length and
  remains far below single-`PutObject` limits. The first version therefore does not add
  `@aws-sdk/lib-storage` or multipart state at all.

The first-version commands are `PutObject`, `HeadObject`, ranged `GetObject`, and `DeleteObject`.
`PutObject` uses `IfNoneMatch: '*'`; `409`/`412` is followed by HEAD and integrity verification, never an
unconditional overwrite. Because third-party checksum support differs, configure SDK request checksums only
when required and treat the PostgreSQL SHA-256 plus a bounded post-write full-stream verification as the
cross-provider integrity truth. ETags remain transport metadata.

MinIO is the CI compatibility baseline. The configurable endpoint, region, credentials, prefix, and path-style
surface may work with R2, B2, and AWS S3, but each provider is advertised as verified only after an explicit
smoke. The project does not yet provide an S3 provider doctor command. Unsupported conditional creation makes
copy fail closed rather than falling back to HEAD followed by an unsafe overwrite.

- [AWS conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)
- [AWS SDK for JavaScript v3 S3 checksums](https://docs.aws.amazon.com/sdk-for-javascript/v3/developer-guide/s3-checksums.html)
- [Cloudflare R2 S3 compatibility](https://developers.cloudflare.com/r2/api/s3/api/)
- [Backblaze B2 S3-compatible API](https://www.backblaze.com/docs/cloud-storage-s3-compatible-api)

## 9. Minimum sufficient verification

Local iteration runs only:

- affected storage/worker/public-reader/policy unit tests;
- affected PostgreSQL 18 integration files;
- migration generation/drift check;
- lint and typecheck;
- one temporary S3-compatible operational smoke after the vertical flow exists.

CI owns:

- the complete PostgreSQL 18 integration suite;
- one S3-compatible fixture covering put/head/range/delete, interruption, mismatch, and recovery;
- local-only regression, workspace build, Storybook, Compose validation/smoke, and upgrade migration;
- CLI/Admin permissions and redaction.

The one manual operational smoke is:

1. copy one verified local blob to S3;
2. interrupt and resume a second copy;
3. remove or hide one location and restore it;
4. protect a shared blob;
5. run prune dry-run and confirm zero mutation;
6. apply one unprotected eviction;
7. read through the remaining location, then confirm original-message fallback when both are unavailable.

No live Telegram download, full local browser matrix, or repeated full integration suite is required.

## 10. Documentation and rollback

Chinese and English operations docs must cover:

- configuration, permissions, credentials, endpoint compatibility, redaction, and rotation;
- byte budgets, request/egress implications, migration, restore, protect, prune, and audit;
- database/object backup consistency and provider lifecycle-policy interaction;
- disabling S3 and returning to local-only;
- rollback at every additive phase.

Before destructive cleanup is ever considered, rollback is:

1. stop mutation workers;
2. wait for or reconcile active location leases;
3. keep at least one verified healthy location per required object;
4. switch read priority/configuration to the retained backend;
5. disable S3 and restart server/worker;
6. preserve additive tables for diagnosis rather than dropping state.

## 11. Explicit non-goals

- No provider-specific lifecycle system becomes the authoritative ledger.
- No multi-region replication, S3-to-S3 migration, CDN/custom domain, versioning workflow, object lock, or
  cross-cloud mirroring in the initial contract.
- No arbitrary filesystem/NFS adapter and no multi-worker horizontal scaling contract.
- No change to G2.3 media kinds, size limits, thumbnail recipe, canonical archive, or Telegram ingestion.
- No G2.5 search/RSS, G2.6 Astro adapter, G2.8 full archive recovery, article publishing, Agent publishing,
  comments, private channels, MTProto, or user session.
