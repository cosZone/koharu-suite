# G2.8 — Portable archive export, import, and recovery drill

- Status: Design accepted — implementation not started
- Issue: [#51](https://github.com/cosZone/koharu-suite/issues/51)
- Parent roadmap: [#1](https://github.com/cosZone/koharu-suite/issues/1)
- Blocked by: G2.2, G2.4, G2.5, G2.7

## 1. Outcome

G2.8 gives an Owner a portable, versioned content archive that can move between koharu-suite instances without
copying authentication state, deployment secrets, or internal database identities. Both `kodama` and Owner Desk
must support the complete flow:

1. estimate and export a point-in-time snapshot;
2. inspect the artifact without mutating an instance;
3. upload or select an artifact and run a mandatory dry-run;
4. resolve run-level conflicts explicitly;
5. apply into an empty or populated target;
6. verify messages, revisions, Telegram formatting, visibility, and optional original media;
7. resume or safely cancel interrupted work.

This replaces the old user-facing `pg_dump`/restore proposal. PostgreSQL dumps remain an operator-level disaster
backup documented separately; they are not a cross-instance format or a substitute for the portable contract.

## 2. Inherited contracts

These are not reopened by G2.8:

- PostgreSQL remains authoritative for canonical messages, revisions, source evidence, visibility, and the media
  ledger while an instance is running.
- A portable message identity is Telegram Chat ID + Telegram Message ID. Database UUIDs are deployment-local.
- Message revisions are immutable. Import may add proven revisions or match existing revisions; it must not
  silently rewrite divergent history.
- `messages.tombstoned_at` controls public visibility. Hidden content remains recoverable and must never leak
  through public API, RSS, search, or media reads during an incomplete import.
- Original media identity is SHA-256 + byte length + detected MIME. Backend keys, locations, provider metadata,
  leases, and priorities are deployment state rather than portable content.
- Bot allowlist state is operational policy. Importing a channel must not enable Telegram collection.
- Derived HTML, search results, RSS, thumbnails, and other recipes are reproducible and must not become a second
  portable source of truth.
- Owner/Auth records, sessions, API keys, bot tokens, CORS policy, storage credentials, and other secrets never
  enter an archive.

## 3. Scope and non-goals

### In scope

- channel metadata;
- canonical messages and all revisions;
- Telegram entities and rendering inputs;
- media metadata and stable source information;
- public/hidden state and its change timestamp;
- optional source provenance selected for the exported content;
- optional verified original media bytes;
- CLI and Owner Desk export/import;
- empty restore and idempotent merge;
- durable transfer jobs, resumable browser transfer, expiry, cancellation, and recovery;
- corruption, hostile-archive, authorization, and recovery-drill validation.

### Out of scope

- Owner/Auth/session/audit migration;
- deployment configuration and Telegram allowlist migration;
- time-range or partial-revision export;
- generated HTML/index/feed/thumbnail export;
- per-message GUI conflict editing;
- custom password encryption, built-in signing, or a new cryptographic container;
- replacing PostgreSQL disaster backups.

## 4. Archive contract

### 4.1 Container

The portable artifact is one `.tar.zst` file. Its logical layout is versioned independently from the application:

```text
manifest.json
checksums.sha256
data/channels.jsonl
data/messages.jsonl
data/revisions.jsonl
data/revision-media.jsonl
data/provenance/*.jsonl          # optional
blobs/sha256/ab/cd/<sha256>      # optional original media
```

Exact filenames may be extended before format v1 is frozen, but v1 must preserve these boundaries:

- the manifest declares format/schema versions, exporter version, created time, snapshot boundary, selection,
  enabled optional sections, counts, logical byte totals, and missing-media summary;
- JSONL records use bounded schemas and logical references, not PostgreSQL UUIDs;
- payload files and blobs are listed in `checksums.sha256` with byte lengths and SHA-256;
- the completed artifact SHA-256 and byte length are recorded by the export run outside the artifact;
- record order is deterministic so semantically equal snapshots are diffable after decompression;
- the artifact is first written under a server-generated staging name, fsynced, verified, atomically finalized,
  and created with mode `0600`.

### 4.2 Compatibility

- The importer accepts the current format and explicitly supported older formats.
- Older formats are upgraded through bounded, tested format migrations before application.
- An unknown newer format fails closed with the minimum koharu-suite version when known.
- Unknown fields may only be ignored where the format schema explicitly marks an object extensible.
- Checksums, declared lengths, record counts, and logical references are validated before staging can become
  eligible for apply.

### 4.3 Portable identity and generated data

- Channels use canonical Telegram Chat IDs; title and username are mutable metadata.
- Messages use `(telegramChatId, telegramMessageId)`.
- Revisions preserve revision number, text, entities, content kind, edit time, author signature, media group, and
  current-revision selection. Internal revision/message/channel UUIDs are remapped.
- Portable media records preserve position, kind, MIME/name/size/dimensions/duration, Telegram locator,
  availability, and bounded source metadata.
- HTML, renderer version outputs, public URLs, backend locations, LRU/access data, work queues, and derived media
  are rebuilt rather than restored.

## 5. Export semantics

- The default selection is every archived channel and every public or hidden message in those channels.
- `--channel` is repeatable. G2.8 does not add time-range export because it would create incomplete revision and
  visibility histories.
- A repeatable-read point-in-time snapshot fixes metadata membership. Messages arriving after the snapshot
  boundary belong to the next export; the worker is not paused.
- Canonical content is always present. `--include-provenance` adds only source observations/updates reachable
  from selected content and never Owner audit or credentials.
- Media metadata is always present. `--include-media` adds verified, currently readable original blobs for both
  public and hidden messages.
- Export estimates selected counts and readable media bytes before work begins. There is no implicit media cap;
  optional `--max-media-bytes` fails the run before artifact creation if the estimate exceeds the limit.
- A blob that disappears or fails verification after estimation becomes a bounded missing-media warning. Content
  export still succeeds and keeps its source fallback metadata; no corrupt or partial bytes enter the artifact.
- Existing output files are not overwritten without an explicit operator choice.

CLI surface:

```text
kodama archive export
kodama archive inspect
```

## 6. Import semantics

### 6.1 Validation and staging

`kodama archive import` is dry-run by default. It performs container safety checks, checksum/schema validation,
logical reference validation, target comparison, capacity checks, and a conflict plan before any public state is
changed. `--apply` consumes the accepted plan through a durable staging run.

The importer supports:

- empty-instance restore;
- idempotent replay of the same artifact;
- merge into an existing instance;
- restart/resume without duplicated messages, revisions, observations, or blobs.

Staged content is not eligible for public reads. The final metadata transition is committed only after the
accepted plan is complete enough to satisfy its visibility and media contracts. Content-addressed media writes
may occur before that transaction and remain safe to deduplicate or garbage-collect after a failed run.

### 6.2 Conflict policy

- A new message adopts the archive visibility state.
- An existing message with different visibility is reported and unchanged unless `apply visibility` is selected.
- Divergent message/revision history makes apply fail before mutation by default.
- A run-level `keep-target` or `use-archive` strategy may be selected explicitly; v1 has no per-message editor.
  `use-archive` may append/remap divergent archive revisions and select the archive-equivalent current revision,
  but it must not delete or rewrite the target's immutable revision history. The resolution is recorded on the
  transfer run.
- An existing channel keeps target title/username by default and reports differences. `apply channel metadata`
  explicitly accepts archive metadata.
- Imported channel content is readable according to message visibility, but the channel is not added to or
  enabled in `telegram_channel_allowlist`.

Every dry-run/apply report separates created, matched, stale, conflicting, visible, hidden, media-present,
media-missing, and regenerated counts. A concise run summary is retained in PostgreSQL; full reports can be
written or downloaded as JSON without storing archive content in the run table.

## 7. Optional media transport

- Only verified original blobs are portable. Thumbnail/transcode variants and recipes are regenerated.
- Blob paths derive from SHA-256 and are never trusted from source metadata.
- One blob is stored once even when referenced by many revisions, messages, or channels.
- Import streams bytes through the existing persistent-backend contract, recomputes SHA-256 and length, and only
  finalizes a ready location after backend verification.
- Local and S3-enabled instances may exchange the same archive; backend IDs, object keys, ETags, versions,
  priority, capacity, and leases are not restored.
- A metadata-only archive remains a valid full content archive. Missing bytes preserve media metadata and the
  existing original-message fallback rather than fabricating readiness.

## 8. Durable transfer jobs

G2.8 introduces an independent transfer-job model. It may reuse the proven lease/state-machine design of media
commands, but it must not extend the media-specific command enum or depend on `MEDIA_CACHE_ENABLED`.

A transfer job records:

- export/import kind and uploading/pending/running/succeeded/failed/cancelled state;
- sanitized options and format version;
- item/byte progress and current phase;
- artifact ID, SHA-256, byte length, expiry, and staging/final state;
- lease owner/token/expiry, attempt, cancellation request, result/error summary, and timestamps;
- Owner initiator identity for authorization and accountability, without placing account data in the artifact.

Only one archive export or import job runs per instance. A conflicting request receives a clear busy response
rather than silently queueing unbounded disk work. Worker restart may reclaim expired leases and resume at an
idempotent checkpoint. Cancellation is token-fenced, stops future work, preserves committed canonical data, and
cleans temporary state safely.

Artifacts and uploads expire after 24 hours by default. The duration is configurable; Owner Desk displays byte
usage and expiry, permits early deletion, and a bounded cleanup job removes expired unreferenced files.

## 9. Admin API and browser transfer

The exact route names are implementation details, but the API must expose these capabilities:

1. create export and receive `202 + job ID`;
2. create an import upload session;
3. query and compare the current upload offset;
4. stream ordered chunks with offset compare-and-swap;
5. finalize and checksum the upload before it becomes importable;
6. inspect/dry-run, select run-level conflict options, and apply;
7. poll job state, request cancellation, download a report, download an artifact, and delete an artifact.

Uploads stream directly to a server-generated staging file. They must not use JSON, `formData()`, `arrayBuffer()`,
or another whole-body buffer. The server enforces configured and free-space limits, declared and observed lengths,
chunk offsets, timeouts, quotas, exclusive creation, no-follow filesystem behavior, fsync, checksum, and atomic
finalization. Proxy limits/timeouts are documented but never treated as the only enforcement layer.

Completed artifacts are immutable. Authenticated downloads reuse the existing streaming response pattern with
Content-Length, ETag, Range/If-Range, 206/416, `Content-Disposition: attachment`, `nosniff`, and
`Cache-Control: private, no-store`. No artifact is placed under Admin static assets or exposed through a public
or bearer-by-ID URL.

## 10. Owner Desk experience

Owner Desk must make the full v1 flow possible without a terminal:

- export form with all-channel default, channel multi-select, include-media, include-provenance, optional media
  maximum, and count/size estimate;
- durable phase and byte/item progress, refresh-safe polling, cancellation, failure detail, retry/resume state,
  artifact expiry, download, and delete;
- resumable chunk upload with progress and explicit retry;
- inspect/dry-run summary listing manifest identity, channels, messages, revisions, public/hidden state, media,
  missing bytes, compatibility, and conflicts;
- one final confirmation screen for run-level content strategy, visibility application, and channel-metadata
  application;
- clear success report and links to imported channels/content.

The existing Owner Desk status poller, 202 receipt, progress, badge, card, and lane patterns should be reused.
Binary upload/download needs a dedicated streaming client rather than the JSON-only `fetchJson` helper.

## 11. Security and privacy

- Create/upload/report operations require an authenticated Owner Session.
- Every custom Admin mutation enforces same-origin/CSRF protection rather than relying on Better Auth route
  behavior implicitly.
- Creating an export that contains hidden content, downloading an artifact, applying an import, and deleting an
  artifact require recent step-up authentication. If 2FA is enabled, step-up includes 2FA.
- Artifact paths and filenames are server-generated; user paths, archive paths, and names never select arbitrary
  host files.
- Extraction rejects absolute paths, `..`, duplicate normalized names, device entries, symlinks, hardlinks,
  unsupported entry types, excess entry counts, excess expanded bytes, and excess compression ratios.
- Logs, API errors, run rows, and audit events contain IDs/counts/sanitized codes, not message text, raw source
  bodies, storage credentials, or host paths.
- The artifact is not encrypted by koharu-suite v1. Documentation requires secure storage and provides `age` and
  GPG examples for transport outside the trusted host.

## 12. Delivery Goals

Each Goal is an independently reviewable and demonstrable PR. A later Goal may begin only after the contracts it
depends on have passed review and targeted verification.

### G2.8.1 — Archive contract

- Freeze format-v1 schemas, logical identities, layout, checksum rules, compatibility policy, limits, and threat
  model.
- Add fixtures and parser/validator tests, including hostile archives.
- No production export/import mutation yet.

### G2.8.2 — Core export and inspect CLI

- Implement point-in-time canonical/provenance export without media bytes.
- Implement deterministic artifact finalization and `kodama archive inspect`.
- Verify public/hidden and revision counts against PostgreSQL.

### G2.8.3 — Safe import engine

- Implement validate → stage → dry-run → apply for empty restore and merge.
- Add UUID remapping, idempotency, revision/content/visibility/channel conflict behavior, and derived-data rebuild.
- Prove no partial public exposure under failure.

### G2.8.4 — Optional media transport

- Add estimate, include-media, max-media-bytes, verified blob packaging, missing-media report, and backend-neutral
  restore.
- Test Local → Local, Local → S3, S3 → Local, dedupe, corruption, and derived regeneration.

### G2.8.5 — Durable transfer jobs and APIs

- Add transfer jobs, leases, checkpoints, cancellation, TTL cleanup, upload sessions, Range download, authorization,
  CSRF, and step-up gates.
- Prove restart, disconnect, disk-full, expiry, and concurrent-request behavior.

### G2.8.6 — Owner Desk archive GUI

- Deliver the complete export/import flows in §10.
- Reuse the existing Owner Desk components and lifecycle utilities before adding new primitives.
- Verify keyboard, focus, progress, interruption, error, and confirmation states.

### G2.8.7 — Hardening, docs, and recovery drill

- Run CLI/API/GUI and Local/S3 end-to-end suites plus hostile-input/security review.
- Publish separate Chinese and English beginner guides for export, import, encryption wrapper, rollback, cleanup,
  and troubleshooting.
- Restore a real sanitized artifact into a fresh Compose environment and preserve commands, JSON reports, hashes,
  screenshots, failure/rollback notes, and Owner acceptance evidence.

## 13. Verification baseline

At minimum, the finished Goal must prove:

- identical logical content after fresh restore;
- all revisions/entities and current-revision selection retained;
- hidden messages remain hidden and public media cannot bypass tombstones;
- imported channels do not start collection automatically;
- repeated import is idempotent;
- default conflicts do not mutate target content;
- bundled blobs preserve SHA-256 and work across configured backends;
- metadata-only and missing-media archives retain valid source fallback;
- unknown versions, corrupt checksums, malicious paths, quota excess, CSRF, expired sessions, and unauthorized
  downloads fail closed;
- refresh, disconnect, cancellation, worker restart, and server restart do not expose partial data;
- expired artifacts are removed without deleting canonical imported content.

## 14. Rollout and rollback

- Schema changes are additive. Existing ingestion, public reads, Telegram Desktop import, media cache, search/RSS,
  and Astro integration continue to run when no transfer job exists.
- Export is read-only. Enabling the feature cannot change canonical content.
- Import apply remains separately gated after upload, inspect, and dry-run.
- A code rollback may leave additive transfer tables and expired staging files; old server/worker versions ignore
  them. Cleanup instructions must not delete canonical media blobs or message data.
- Before the first production apply, retain the normal PostgreSQL operator backup and record current image digest.
- G2.8 is not complete until the fresh-environment recovery drill and rollback path have Owner acceptance.

## 15. Accepted design gate

The design was accepted on 2026-08-03 through four complete decision rounds. There are no open product gates.
Implementation may refine internal names and schemas, but changing scope, conflict defaults, security gates,
artifact semantics, GUI availability, or failure visibility requires reopening this Goal before code proceeds.
