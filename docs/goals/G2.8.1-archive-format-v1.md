# G2.8.1 — Freeze portable archive format v1

- Status: Complete
- Issue: [#53](https://github.com/cosZone/koharu-suite/issues/53)
- Parent Goal: [#51](https://github.com/cosZone/koharu-suite/issues/51)
- Parent design: [G2.8 portable archive](./G2.8-portable-archive.md)

## 1. Outcome

G2.8.1 freezes the portable wire contract and ships a DB-independent internal package that later Goals use for
export, inspect, and import. The package owns schemas, deterministic JSONL, checksums, container entry policy,
streaming `.tar.zst` parsing, cross-record validation, and sanitized reports.

This Goal intentionally performs no PostgreSQL reads or writes and exposes no production CLI command. It is
complete when a valid synthetic archive can stream through the format layer and every malformed, inconsistent,
or hostile fixture fails before any record can become eligible for import.

## 2. Package boundary

The implementation lives in private workspace package `@koharu-suite/archive-format`.

It may depend on:

- Node standard library streams, crypto, and Zstd;
- `tar-stream` for streaming tar headers/entries without filesystem extraction;
- Zod for strict wire schemas.

It must not depend on:

- `apps/server`, Drizzle, PostgreSQL, GrammY, Better Auth, Hono, or Owner Desk;
- `@coszone/koharu-astro` public response schemas;
- database inferred rows, deployment UUIDs, local source paths, backend locations, or runtime jobs.

Later server adapters map Date/BigInt/database rows into UTC/decimal-string wire records. Keeping that mapping
outside the package prevents storage schema changes from silently changing archive format v1.

## 3. Codec decision

Koharu-suite already requires Node `>=22.20.0`; Node has provided streaming Zstd transforms since 22.15.0.
G2.8.1 therefore uses `node:zlib` `createZstdCompress`/`createZstdDecompress` and does not add a native Zstd addon.
Runtime construction performs an explicit capability assertion because the Node 22 API is still experimental.

Tar parsing uses pinned `tar-stream@3.2.0`. It emits header + byte stream and does not choose filesystem targets.
The package never calls a general-purpose extract-to-directory API. V1 accepts canonical USTAR names up to 100
bytes and rejects PAX/GNU extension headers; every accepted header name is normalized, checked, budgeted, and
matched to the v1 layout before its bytes reach a consumer.

The streaming read pipeline is:

```text
compressed input counter
→ Zstd decompressor with bounded window
→ expanded byte/ratio counter
→ tar header parser
→ entry type/path/order/size policy
→ checksum and schema consumer
```

## 4. Wire rules

- Bigints are base-10 strings with canonical sign/no-leading-zero rules; JavaScript numbers never carry Telegram
  identifiers.
- Timestamps are canonical UTC strings and round-trip through `Date#toISOString()` without normalization drift.
- JSONL is UTF-8, one strict JSON object per LF-terminated line, with no blank lines.
- `manifest.json` and every JSONL line use the v1 canonical JSON serializer exactly; semantically equivalent
  non-canonical key order and duplicate JSON keys are rejected.
- Every v1 object is strict. V1 carries no catch-all `extensions`, arbitrary metadata, or raw-update object;
  future portable fields require a reviewed schema/format revision rather than being silently copied.
- Records use logical channel/message/revision/media identities. No database UUID or foreign key is portable.
- Telegram identifiers are bounded signed-int64 decimal strings. Logical IDs sort numerically; revision and media
  positions sort numerically; archive paths and JSON keys use locale-independent code-unit ordering.
- Unknown Telegram entity `type` strings may be preserved, but the entity object itself has a bounded known shape.
- Optional provenance is a typed Telegram source projection: logical source identity, observation time, bounded
  source type, and media locators. Raw source bodies, Owner audit, credentials, and host paths never enter v1.
- Canonical JSON sorting is versioned independently from existing message content fingerprints. G2.8.1 does not
  move or modify the server's current message fingerprint implementation.

V1 uses deterministic, zero-based, six-digit JSONL shards. Empty sections have no empty shard; every present shard
contains at least one record, indexes are contiguous, and ordering continues across shard boundaries:

```text
data/channels/000000.jsonl
data/messages/000000.jsonl
data/revisions/000000.jsonl
data/revision-media/000000.jsonl
data/provenance-observations/000000.jsonl  # optional
data/provenance-media/000000.jsonl         # optional
```

The default shard target is at most 50,000 records and 64 MiB of raw JSONL bytes. These are encoder targets rather
than parser trust: the manifest declares every actual shard's family, path, record count, and byte length, and the
validator independently enforces its configured finite limits.

After the two control entries, tar order is uniquely fixed: JSONL entries appear in exact `manifest.files` order,
then content-addressed blobs appear in code-unit path order. Blob paths are
`blobs/sha256/<first-two>/<next-two>/<lowercase-sha256>`, and the checksum digest must equal the path digest.

## 5. Integrity model

`manifest.json` is the first entry. `checksums.sha256` is the second entry.

- Manifest declares format/schema/exporter versions, snapshot, selection, sections, counts, logical bytes,
  missing-media summary, an ordered JSONL file inventory, and the checksum-file SHA-256/length.
- The checksum file lists every remaining data/provenance/blob entry exactly once and excludes itself and the
  manifest.
- Every non-control entry must be listed; every listed entry must occur; duplicate checksum paths and duplicate
  effective tar paths fail.
- Declared and streamed length, SHA-256, record count, section count, and cross-record references all agree before
  validation succeeds.
- An export run later stores the complete artifact hash and length outside the archive. V1 checksums detect
  corruption and inconsistency, not publisher authenticity; G2.8 deliberately does not add signing.
- Checksum verification uses exact raw entry bytes. Parsing and reserializing JSON is never a checksum substitute.

Large JSONL sections use deterministic bounded shards so a single tar entry and a single retry unit remain
bounded. Entry and record order are canonical and tested with fixed snapshot/export timestamps.

`missingMedia.references` counts logical media references whose original bytes are absent. When a missing original
has a verified identity, `uniqueObjects` deduplicates by SHA-256 + length + detected MIME and `knownBytes` sums each
unique object once. Unknown identities contribute only to `references`. Two records may share one included blob,
but the same SHA-256 with conflicting length or detected MIME fails validation.

Canonical JSON uses a small generic profile for record payloads and a separate finite manifest profile that admits
the declared 100,000-entry inventory. The manifest profile remains bounded by the 32 MiB high-level manifest limit;
it is not a general escape hatch for provenance or record data.

## 6. Default safety policy

All limits are finite and grouped into format/model and container policies. Callers of the high-level v1 archive
validators may lower the hard ceilings but cannot raise them at runtime. Raising a v1 trust-boundary ceiling
requires an explicit, reviewed format-package revision. Lower-level codec/container primitives still require
explicit positive finite limits and never decide archive eligibility on their own; they may use controlled non-v1
limits in tests or writer preparation, but production import/inspect must pass through the high-level validator.

| Limit | Default |
| --- | ---: |
| compressed archive bytes | 8 GiB |
| expanded tar bytes | 16 GiB |
| entries | 100,000 |
| one entry | 8 GiB and remaining expanded budget |
| path | 100 bytes / 16 segments |
| one JSONL line | 4 MiB |
| target JSONL shard | 50,000 records / 64 MiB |
| all model records | 1,000,000 |
| manifest | 32 MiB |
| checksum file | 20 MiB |
| compression ratio | 100:1 with a 1 MiB compressed-byte denominator floor |
| Zstd window log | 27 (128 MiB) |
| no-progress timeout | 30 seconds |

These are parser resource ceilings, not silent product media caps. An archive that exceeds a ceiling fails with a
clear report and is never partially accepted. Future export/UI estimates must surface the active limits before
starting work.

## 7. Hostile input contract

V1 accepts regular files only. It rejects directory, symlink, hardlink, FIFO, block/character device, socket,
sparse, and unknown entry types.

Effective USTAR entry paths must be strict relative POSIX paths. Reject PAX/GNU long-name extensions and:

- absolute, `//`, URI-like, Windows drive/UNC, backslash, NUL/control, invalid UTF-8;
- empty, `.`, `..`, trailing-slash, or over-depth segments;
- duplicate canonical names and ASCII-case-fold collisions;
- entries absent from the declared v1 layout or checksum index;
- extra concatenated tar archives or non-zero trailing data.

The parser enforces header, entry, expanded, compressed, record, line, ratio, and Zstd-window limits while bytes
flow. It aborts immediately on truncation, checksum mismatch, no-progress timeout, cancellation, or consumer
failure and closes every pipeline resource.

## 8. Validation layers

1. Container layer validates Zstd/tar structure, resource policy, entry type/path/order, and raw bytes.
2. File layer validates manifest, checksum grammar, JSONL framing, schemas, lengths, hashes, and counts.
3. Model layer validates uniqueness and logical references: channel → message → revision → media/provenance/blob.
4. Report layer emits versioned counts and bounded sanitized issue samples, including safe archive path, JSONL line,
   and byte offset when known. It never includes entry bodies, message text, raw provenance, host paths, or
   secret-like values.

Revision numbers start at 1 and remain contiguous per message; media positions start at 0 and remain contiguous per
revision. `text` revisions have no media, `caption` revisions have text and media, and `none` revisions have media
but no text/entities. Entity ranges are checked against JavaScript/Telegram UTF-16 code-unit offsets. Bot source
records require both Telegram file IDs; Desktop source records carry neither and never carry an exported host path.
For Desktop metadata-only media, the portable fallback remains the Telegram source message, not a source-machine
filesystem location.

Provenance observation identity is message/revision reference plus its complete source discriminant. A null revision
is a message-level observation; a non-null revision must exist. Provenance media must match one exact observation and
uses zero-based contiguous positions per observation. Observation/media ordering uses the logical message, nullable
revision, source discriminant, then media position. Storage identity remains aligned with the existing database
contract: Bot observations are globally unique by update ID, while Desktop observations use export-file digest plus
source chat/message IDs. Bot `updateType` remains part of the exact media-to-observation match even though it is not
part of the storage-unique key. All provenance metadata/payload objects are strict typed projections; the canonical
message/revision records already carry user-visible text, entities, and media metadata.

`missingMedia` is recomputed only from logical `revision-media` records. All references with the same known SHA
must agree on length, detected MIME, and `included`; included references require exactly one matching blob, while
excluded references forbid that blob. Unreferenced blobs fail validation.

The model validator performs no database writes and exposes no per-record eligibility callback. A later importer
may stage streamed records transactionally, but it cannot make them importable until the complete container,
checksum inventory, EOF, aggregates, and model closure are clean.

The validator retains only bounded identity/index summaries needed for closure. Revision bodies and entity arrays
are reduced immediately to content-kind flags and media counts; blob bytes are hashed and drained as chunks rather
than retained. The fixed one-million-record ceiling bounds these summaries, while the large-stream regression tracks
both V8 heap and external Buffer memory to catch accidental whole-blob buffering.

Current v1 is the first portable format. There is no invented v0 migration. The migration registry is empty and
unknown future versions fail closed. A migration is added only when a real older supported format exists.

## 9. Test fixtures and matrix

Committed fixtures are small logical directories, not opaque multi-megabyte binaries:

```text
test/fixtures/archive/v1/minimal/
test/fixtures/archive/v1/full/
```

Tests generate small tar/zstd and hostile variants in memory. Large streaming fixtures use `mkdtemp`, write only
inside that isolated directory, and clean it after use.

The archive writer contract is prepare + replay: exporters first spool bounded shards/blobs and record their raw
count/length/hash, then write manifest/checksum and replay payloads in canonical order. A one-shot `Readable` is
never implicitly reused, and replayed bytes must still match the prepared evidence.

Required coverage:

- metadata-only public + hidden messages, full revisions/entities/current selection, and missing media metadata;
- optional provenance and two media references deduplicated to one blob;
- Telegram IDs beyond `Number.MAX_SAFE_INTEGER`;
- strict schemas, canonical UTC/decimal/JSONL bytes, and deterministic output;
- missing/extra/duplicate entries and checksum/length/count mismatch;
- duplicate identities and dangling current revision/media/provenance/blob references;
- future format and unknown-field rejection;
- every hostile path/type/truncation/limit/ratio case in §7;
- 100,000 generated JSONL records and a large synthetic stream with bounded heap behavior;
- AbortSignal and consumer-error cleanup;
- versioned, bounded, sanitized report output.

## 11. Non-goals

- PostgreSQL migrations or adapters;
- production export repository/service;
- `kodama archive export`, `inspect`, or `import` wiring;
- staging/apply/conflict mutations;
- media backend reads/writes;
- transfer jobs, Admin APIs, browser upload/download, or Owner Desk;
- compatibility code for a nonexistent pre-v1 portable archive.

## 12. Rollback

The package is additive and unused by production runtime in this Goal. Rolling back removes the package and its
two pinned tar dependencies without touching databases, content, media, configuration, or deployed behavior.
